DigiShield — six architectural cuts

A single Spring Boot application, split into nine modules whose boundaries are enforced by tests, talking to each other through domain events. This document zooms in step by step, from the system as a whole down to the path into production.

Cut 01 · The whole system

One artifact, four roles, three data stores

The React frontend lives in a sibling directory and calls /api/v1. Identity is issued by Cognito; the backend only verifies the JWT. The same jar file runs four different roles — which role it plays is decided by the Spring profile at startup, not by a different build.

Cut 02 · Boundaries

The nine modules may not import each other

This is what separates DigiShield from an ordinary monolith. Each module declares in its package-info.java exactly what it is allowed to depend on — and only contracts and shared appear on those lists. No module names another module.

The consequence: for two modules to talk, the path runs through contracts — either an event or an interface. The boundary does not live in code review, it lives in ModularityTests, which runs in seconds and needs no Docker.

Cut 03 · The mechanism

How one phishing click spreads

If you read only one diagram, read this one. It is the entire reason the event architecture exists: simulation has no idea that learning, analytics or notification exist. It records that something happened and publishes it.

To add a new reaction to the click — opening a SOC ticket, say — you write one more listener. Not a single line changes inside simulation.

Cut 04 · Inside one module

Five layers, but only one is visible from outside

All nine modules share exactly the same directory structure. The point is not that there are five layers — it is that only api/ is the public surface. Entities, repositories and service implementations sit behind that wall; a module that imports them turns the build red.

Cut 05 · Cross-cutting

Tenant isolation in two layers, not one

DigiShield is multi-tenant — many organisations share one database — so a leak between two organisations is the worst failure the system can have. Hence two independent barriers: if a developer forgets WHERE tenant_id = ?, PostgreSQL still stops it one layer down.

Cut 06 · The path to production

From commit to the Jetson cluster

One workflow at the monorepo root, sequential and fail-fast — a failure at the third stage means the four after it burn no runner minutes. CD runs only on a push to main, and it does not deploy by the latest tag: it pins sha-<commit> into the manifest and pushes that to the branch ArgoCD watches.

In review

The four decisions that make this architecture

Decision What it buys What it costs
Modular monolith
over microservices		 One deployment, one transaction, and cross-module refactors the compiler still keeps honest. No per-module scaling; one badly broken module takes the whole process with it.
Boundaries enforced
by tests		 Nothing rests on human discipline — a violation shows up within seconds. One more structure to learn; taking a shortcut means editing package-info.
Events instead of
direct calls		 New reactions without touching the publisher; genuinely loose coupling. Business flows can no longer be read by hitting “go to definition”.
Two-layer
tenant isolation		 A single programming mistake is not enough to leak data between organisations. Dev runs on H2 and so lacks layer 2 — integration tests on a real Postgres cover the gap.

In short: one Spring Boot application running four roles by profile, holding nine modules whose boundaries are enforced by tests, talking through ten domain events, with data isolated in two layers and shipped to production by GitOps on SHA-pinned images.
